    fix(security): stop telling developers to bundle .env as an asset (#126)
    
    The configuration docs and the pubspec comment told readers to add `- .env`
    to the Flutter asset list so flutter_dotenv could read it. A Flutter asset
    declaration is not build-mode scoped, so that ships the file inside the
    release APK, the release IPA and the web build - extractable with unzip, and
    on web fetchable unauthenticated at /assets/.env.
    
    Removing the instruction alone would leave web users with no configuration
    mechanism at all, so this states the safe path instead:
    
    - native, every build mode: `--dart-define-from-file=.env`. The same file is
      consumed as a build input without ever becoming an asset. Stated honestly:
      a dart-define is still compiled into the binary and recoverable from it, so
      it is build configuration, not a secret store.
    - web: there is no dart-define path (EnvConfig guards every read with
      `!kIsWeb`) and a web client cannot hold a secret at all, because the user
      downloads the whole bundle. Secrets come from the backend; only publishable
      values go in the bundle.
    - an asset-backed .env stays possible for web configuration, but only with a
      committed inline acknowledgement, so it cannot happen silently.
    
    Adds `tool/check_env_assets.dart`, which fails when any env file other than
    .env.example appears under `flutter: assets:`. It runs as a step in
    scripts/dev/audit_template.sh and from test/tooling/check_env_assets_test.dart,
    so `flutter test` - and therefore the CI Quality gate - catches a commit that
    adds one. `.env.example` no longer suggests API_KEY/SENTRY_DSN without a
    warning. No secret is added to the tree and .env stays gitignored.
    
    Refs koniz-dev/flutter-starter#79
